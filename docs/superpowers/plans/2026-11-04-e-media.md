# Lote E — WhatsApp attachments over MCP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A new opt-in MCP tool `get-message-media` that lets Claude read a WhatsApp image (shrunk server-side) or PDF (text extracted server-side) and hands the user the file through a temporary, public, 1-hour download link served by this app.

**Architecture:** Pure, Nitro-free modules (payload classification, names/headers/pages, budgets and ladders, errors, in-memory cache/semaphore/cooldown) carry the decisions and are exercised with plain `node`. Thin Nitro modules wire them: one Evolution download function (verified, capped, de-duplicated, cached) shared by the tool and the public route; a link table in `app`; a third credential path for the route that reuses `resolveMcpAuth`'s token-facts query. No bytes are ever persisted.

**Tech Stack:** Nuxt 4 / Nitro (h3 1.15), postgres.js, zod, `sharp` (images), `unpdf` (PDF text), MCP toolkit 0.19.0. No test framework (CLAUDE.md): `pnpm typecheck` + `node` check scripts on pure modules + real JSON-RPC/HTTP calls against a local harness.

**Spec:** `docs/superpowers/specs/2026-11-04-e-media-design.md` (approved, authoritative). Background: `.superpowers/sdd/2026-11-04-e-media/spec-adversarial-review.md`. ## Review Focus

Failure modes the spec implies but no single task's happy path exercises, most likely first. Each has a pinned test in the task named.

1. **RF1 — id exists but not for this token:** same `key.id` in an out-of-scope chat, only via `remoteJidAlt`, or a scoped token with an empty allowlist → exactly the same 404 text as a nonexistent id (T8 query, T11 tests).
2. **RF2 — attachment metadata lies or is odd:** `fileLength` absent/`"0"`/string, `mimetype` absent or wrong (`application/octet-stream` named `.pdf`; `image/png` that is really SVG), `fileSha256` stored in an unexpected shape or absent → never a crash, never a silent "verified" (T2, T8, T11).
3. **RF3 — hostile or odd bytes:** pixel bomb, 500-page PDF, encrypted/corrupt/truncated PDF, 0-byte or garbage image, CMYK, EXIF-rotated, transparent PNG → link-only with an honest `note`, process alive (T9).
4. **RF4 — link abuse and edges:** `HEAD`, `Range`, double tap, 21st download, the exact expiry second, per-IP rate limit with a spoofed `X-Forwarded-For`, token in the log line of an error path (T12).
5. **RF5 — names and headers from a hostile sender:** empty name, Evolution's `ID.false` fallback, CRLF, U+202E, 300 characters, non-ASCII, `../` (T3, T12).
