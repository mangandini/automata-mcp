# Lote B — Búsqueda completa Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `search-messages` y `read-messages` ignoran acentos, aceptan número como chat, paginan con ventana fija, filtran por autor (nombre) en grupos, encuentran por nombre de archivo y leen contexto alrededor de un mensaje; más guía de búsquedas para el usuario.

**Architecture:** Un módulo puro (`search-text.ts`) genera el plegado para JS y SQL desde una sola fuente. `evolution-db.ts` (único SQL) gana opciones (`match`, `jids`, `author`, `page`, total, `around`). Dos módulos nuevos: `chat-target.ts` (número → formas del chat, con scope) y los helpers de autor en `mentions.ts`. Los tools solo cablean. Todo es solo lectura, sin migraciones.

**Tech Stack:** Nuxt 4 / Nitro, postgres.js (conexión de solo lectura a la BD de Evolution), zod, MCP toolkit 0.19.0. Sin framework de tests: `pnpm typecheck` + scripts `node` sobre módulos puros + curl a producción (Task 11).

**Spec:** `docs/superpowers/specs/2026-10-22-b-search-design.md` (aprobada). Hechos del código en "Notas de código" abajo.

## Global Constraints

- Branch `feat/b-search`; nunca push a `main` sin OK explícito del usuario; no push durante importaciones de historial (`OPS.md`).
- Scope = predicado en el SQL, **antes** de contar/paginar; falla cerrado. `total`, `hasMore`, candidatos de autor y `note` no pueden revelar nada fuera de scope.
- **Nunca normalizar JIDs localmente**; los números se resuelven con `resolveNumberToJid` (`mcp-scope.ts`).
- Dedupe: `DISTINCT ON (m.key->>'id')` dentro del CTE; `LIMIT/OFFSET` fuera; orden `"messageTimestamp" DESC, key->>'id' DESC`; `bestNamed()` determinista.
- Solo rutas jsonb explícitas (nada de `$.**`). Consultas parametrizadas; ningún texto del llamador se concatena en SQL; sin escritura; sin extensiones nuevas en la BD de Evolution.
- `hasMore` sale de `limit + 1` filas, nunca de `total`. `totalMatching` ausente = "no medido".
- Un id (jid/LID/número) nunca se presenta como nombre (`meaningfulName`).
- Tools sin argumento de conexión; `defineKindTool`; basenames únicos.
- `search-text.ts` es puro (sin auto-imports de Nitro): cargable con `node`.
- Texto de `description`/`note`/errores de los tools en inglés; comentarios explican el *porqué*, estilo de `evolution-db.ts`.
- Commits terminan con:
  `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`
  `Claude-Session: https://claude.ai/code/session_01Kjjdy1CDhDnPrZEXZKTHSZ`
- Nunca crear sesiones/usuarios/tokens escribiendo en la BD; nunca imprimir tokens de `.env`.
- Sin pruebas MCP locales (no hay WhatsApp local). Toda verificación contra producción es de la Task 11 (controlador).

## Review Focus

Entradas que la spec implica y ningún test local cubre; cada una tiene su comprobación en la tarea indicada.

1. Consulta en **mayúsculas con tilde** (`FOGÓN`) y texto **NFD**: debe coincidir con `fogon` (T1 script `node`; T2 SQL).
2. Número con espacios, `+`, guiones, o jid inexistente / sin WhatsApp: error explícito, jamás lista vacía; con scope, mismo error que un chat fuera de scope (T4).
3. Página fuera de rango y `window` reenviada: `chats: []`, `hasMore:false`, sin `nextPage`, con la ventana (T3).
4. Token con `chatJids` vacío y `author`/`around`/número: cero filas, cero conteos, sin revelar (T3, T6, T7).
5. El mismo mensaje almacenado 2–3 veces (copias con distinto `pushName`) con filtro de autor: un solo hit, sin que el filtro lo duplique o lo pierda (T6).
6. Comodines `%` y `_` en la consulta (`escapeLike`) y términos de 1 carácter (error 400 que lo nombra) (T2/T8).
